Deviations from the literal prompt wording (see ADR-012 for full reasoning):

- "Refactor PolicyService to strictly use the YAML loader" → deleted
  PolicyService/AccessPolicy/AccessPolicyRepository outright instead.
  ZteAuthorizationFilter already evaluates YAML directly via PolicyMatcher;
  a YAML-backed PolicyService would just be a second implementation of the
  same logic. ADR-011's own Future Migration Path already said "retiring
  access_policies and PolicyService."
- Refactored InternalPolicyController (GET /api/v1/internal/policies) to
  read from PolicyDefinitionStore instead of leaving/deleting it — not in
  the task list, but zt-agents' GatewayClient depends on this endpoint's
  exact response shape (PolicyDto mirrors the DB row). Traced the caller
  before deleting anything; updated PolicyDto to the PolicyRule shape.
- zt-admin-ui is a plain npm directory, not a Gradle subproject (not added
  to settings.gradle.kts). Root build.gradle.kts's subprojects{} block
  unconditionally applies Java/Spring-BOM config to every included module —
  wrong for a project with no Java sources. The node-gradle plugin is
  applied directly inside gateway-service/build.gradle.kts instead,
  pointed at ../zt-admin-ui via nodeProjectDir.
- SPA redirect_uri points at the literal /admin/index.html (matching the
  prompt's own stated serving URL), not a bare /admin/. An initial attempt
  built a custom PathResourceResolver for the bare-directory case; it
  didn't work (still 404'd) and wasn't even the asked-for URL once
  re-read — removed.

Real bug found and fixed during this session (not anticipated by the plan):
  ZteAuthorizationFilter implements Spring Cloud Gateway's GlobalFilter,
  which only runs for requests routed through a configured
  GatewayRouteConfig route. /api/v1/admin/** is a local @RestController
  with no route entry, so the filter never ran for it at all — a manual
  curl with a USER-role JWT returned 200 from the new admin API before this
  was caught. Fixed with a new, narrowly-scoped AdminAuthorizationFilter
  (a genuine WebFilter, which — unlike GlobalFilter — wraps the whole
  WebFlux dispatch regardless of routing), reusing the same
  PolicyMatcher/PolicyDefinitionStore evaluation. Caught by hand-testing
  with real Keycloak tokens against the running gateway, not by unit tests
  alone — the first fix attempt (switchIfEmpty-based) then hit a second,
  related bug (switchIfEmpty can't detect emptiness through a Mono<Void>
  chain, since a successful Void completion and an empty one look
  identical — double-invoked the 403 write, crashing on the second write
  to an already-committed response). Both bugs, and the fix, are documented
  in AdminAuthorizationFilter's Javadoc and ADR-012, plus pinned down by a
  new AdminAuthorizationFilterTest so they can't silently regress.

Key prompt pattern: for large multi-part specs handed over as a finished
"architect's plan," verify the plan's own factual claims about existing code
behavior (here: "ZteAuthorizationFilter runs as a global filter on every
request") against the running system before trusting them — a claim can be
accurate for every case actually exercised so far (permitAll internal
endpoints) and still be wrong for a new case that actually depends on it.
