Act as a Senior Solution Architect and Software Engineer. We are implementing
the next stage of our Zero Trust API Gateway (ZTeasy) and the Python-based MCP
environment (hubspot-mcp).

Current goal: Implement JWT-based authentication for Agents A and B using
Keycloak (Client Credentials flow), validate the tokens at the ZTeasy gateway
level, and route agent requests to ZTeasy instead of the direct MCP server.

DO NOT implement any forwarding or routing from ZTeasy to the backend MCP
server at this stage. ZTeasy must act as a dead-end that only validates
authentication and returns a stubbed JSON-RPC response.

Follow the mandatory project workflow strictly: THOUGHTS -> implementation ->
CRITIQUE -> ADR -> prompt history -> README/CLAUDE.md updates -> tests ->
commit.

Task 1: ZTeasy Gateway (Kotlin/Spring WebFlux)
- Add the `spring-boot-starter-oauth2-resource-server` dependency to the
  `gateway-service` `build.gradle.kts`.
- Configure application properties to set up the OAuth2 Resource Server with a

  localhost:8080/realms/zteasy-realm).
- Create a `SecurityConfiguration` class with a `SecurityWebFilterChain`.
- Secure the `POST /message` endpoint to require an authenticated user/token.
  Leave `/sse` configuration open or configured for query-param token

  client, log the extracted `clientId` and immediately return a valid dummy

- Write unit tests using `@WebFluxTest` and `spring-security-test` to verify
  that requests without a token return 401 Unauthorized, and requests with a

Task 2: Agent Scripts (hubspot-mcp project in Python)

Task 3: Documentation and ADR

Deviations from the literal brief, resolved during THOUGHTS/CRITIQUE and one
clarifying question (user answered "proceed without breaking existing
contracts"):

- gateway-service is Java, not Kotlin (only zt-agents is Kotlin) — implemented
  in Java to match existing conventions.
- spring-boot-starter-oauth2-resource-server was already a dependency
  (Stage 2/ADR-002); issuer-uri already correctly pointed at
  localhost:8180/realms/zte-realm (not the assumed 8080/zteasy-realm) — added
  agent-a/agent-b clients to the EXISTING realm instead of inventing a second
  one.
- A global SecurityWebFilterChain already existed (auth-library.SecurityConfig,
  auto-configured, anyExchange().authenticated()) and already covered /sse and
  /message per ADR-009 — did not add a competing gateway-local
  SecurityConfiguration.
- Header-based bearer JWT for GET /sse (not query-param) is already "the
  easiest secure option" since agents are plain HTTP clients, not browser
  EventSource consumers.
- Preserved Stage 8's 202-Accepted/SSE-session transport contract rather than
  switching POST /message to a synchronous 200 OK body — the dead-end change
  is scoped to what gets computed (always a stub, policy engine and backend
  never called), not how it's delivered. Updated two of McpProxyIT's existing
  assertions (deny-vs-allow, "backend called once") to match; added
  client-credentials-based scenarios for agent-a/agent-b plus a 401-without-
  token check.
- clientId extraction reads the azp claim first (same claim
  RequestAuditFilter already uses), falling back to sub.
- policyEngine/backendClient/dataMaskingFilter stay wired into
  McpProxyHandler's constructor, unused in this stage, so re-enabling them
  later is a one-method change, not a rewire.
- Rewrote agent_simulator.py entirely: the old stdio-based deal-stage
  read/update/rollback simulation no longer applies now that ZTeasy sits in
  between and stubs every call. New version implements the actual MCP
  HTTP+SSE client protocol (GET /sse handshake -> POST /message -> read
  result off the SSE stream) against the gateway, not hubspot_server.py
  directly.
- No new Python dependency for .env loading — added run_agents.sh mirroring
  the existing run.sh pattern (source .env, then run) instead of pulling in
  python-dotenv.
