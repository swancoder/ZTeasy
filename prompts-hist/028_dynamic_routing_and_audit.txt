---

Deviations from the literal instructions, and why (full reasoning in
ADR-017):

1. **No new `request_logs` table.** The literal instruction
   ("V[DB_VERSION]__create_request_logs.sql ... CREATE TABLE") assumed
   this table didn't exist yet. It does — V4, ADR-013 — complete with
   `agent_id`/`tool_name` columns already reserved, unused, and explicitly
   commented for exactly this future unification. A literal CREATE would
   have failed with a duplicate-table SQL error the first time the
   migration ran. `V12__extend_request_logs.sql` ALTERs the existing
   table with the five genuinely-new columns instead
   (`initiator_client`, `original_user_obo`, `target_service`,
   `http_method`, `decision_effect`) and reuses `path`/`agent_id`/
   `tool_name` for `target_path`/`mcp_tools` rather than duplicating them
   under new names.

2. **No `ServerWebExchangeUtils.cacheRequestBody` machinery.** The
   Self-Criticism's core warning doesn't apply: the MCP proxy
   (`POST /message`) isn't a Spring Cloud Gateway `GlobalFilter`/routed
   path at all — it's a separate WebFlux `RouterFunction` handler
   (`McpProxyHandler`) that already parses the JSON-RPC body exactly once
   and builds an outbound request itself, rather than proxying the
   original byte stream. `agentId`/`toolName` were already extracted
   there; the actual gap was that nothing persisted them anywhere durable
   — fixed by having `LoggingMcpAuditService` also call into
   `RequestLogAuditService`, not by adding new body-caching filter
   machinery that this codebase's MCP path doesn't need.

3. **This is really ADR-009's own flagged "future work."** Rather than
   building a second, MCP-only persistence path, `LoggingMcpAuditService`
   now writes into the same `request_logs` table REST traffic already
   uses, via a new `RequestLog.forMcp(...)` factory alongside
   `RequestLog.forRest(...)` — one unified audit trail, not two parallel
   ones.

4. **`application.yml` had no static routes to remove** — the two
   hardcoded routes were a Java `RouteLocator` bean
   (`GatewayRouteConfig`, deleted entirely), not YAML. `service-a.uri`/
   `service-b.uri` properties were kept, but repurposed: from "the route
   target" to "the bootstrap seed value" consumed by a new
   `InventoryBootstrapSeeder`, so a fresh `docker compose up` still routes
   service-a/service-b out of the box without manual Admin Console
   onboarding.

5. **service-a/service-b are not Keycloak clients calling the gateway as
   themselves** — their real inter-service call is a direct mTLS hop
   (ADR-004), off-gateway, using the OBO token already minted for the
   user's own request. There is no pre-existing "service-a authenticates
   to the gateway" flow to attach a test to. Exercising
   `ServiceToServiceAuthorizationFilter` for real required adding a new,
   clearly-documented `service-a` Keycloak machine client (mirroring
   `agent-a`/`agent-b`'s shape) representing a distinct identity — not a
   stand-in for the real service's own internal call — used only by the
   new `ServiceToServiceIT` test.

6. **`GET /api/v1/service-b/restricted`, not `/hello`** — `service-b` has
   no `/hello` endpoint (that's service-a's greeting endpoint); the
   existing analogous service-b endpoint is `/context`
   (`UserContextController`). Used `/context` as the ALLOW target and
   added `/restricted` (same OBO-validation logic, different policy
   exposure) as the endpoint with no matching rule, to prove default-deny
   rather than requiring an explicit DENY rule.

Two real, previously-latent bugs found and fixed while building and
testing this (full root-cause detail in ADR-017, both discovered via live
debugging with actual evidence, not guessed):

- `@EnableScheduling` was declared on a `@ConditionalOnProperty`-gated
  config class (`MtlsHttpClientConfig`) that never activates when
  `zte.mtls.enabled=false` — true for every integration test. No
  `@Scheduled` method in the entire application, including the
  pre-existing `HealthPollingService`, had ever actually fired during an
  IT test before this. Moved to `GatewayApplication` (always active).
- `ZteAuthorizationFilter`'s service-principal detection required
  `realm_access.roles` to be completely empty, which is never true for a
  real Keycloak client-credentials token (Keycloak grants every client
  default composite/scope roles automatically). Never caught before
  because MCP agents — the only prior service-credential callers — never
  reach this Gateway `GlobalFilter` at all. Fixed by dropping the
  roles-emptiness requirement.
