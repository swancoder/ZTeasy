Original prompt (paraphrased — full text requested CoT/Self-Criticism/ADR
protocol per CLAUDE.md, and gave five numbered task groups plus verification

  We successfully synced Users, Groups, and Roles into the local PostgreSQL
  cache (Stage 13). Now unify the identity model by including OAuth2 Clients
  (machine identities / service accounts) so Agent A, Agent B, and backend
  services appear in the UI and can be strictly validated in YAML policies.

Preceding context: the user asked "why don't I see agents identities amongst
imported ones," pasting a prior session's answer explaining Agent A/B are
OIDC clients authenticated via client credentials, matched by azp against
agentMcpToolCalls rules. My answer at the time: (1) IdentitySyncService never
called Keycloak's /clients endpoint — Users/Groups/Roles was the deliberate
Stage 13 scope; (2) even Keycloak's own /users endpoint (confirmed live)
excludes service-account users, so agent-a/agent-b/zte-gateway's service
accounts wouldn't have shown up as USER-type identities either way; (3) it
wouldn't have mattered for policy purposes since service2service/
agentMcpToolCalls match azp as a raw string, independent of idp_identities.
That gap is exactly what this task closes.

Task groups as given:
  1. Flyway migration — add CLIENT to idp_identities.type (alter the CHECK
     constraint if VARCHAR-backed, alter the enum if a native Postgres enum).
  2. IdpClient.fetchClients() + KeycloakIdpAdapter implementation (Keycloak
     GET /admin/realms/{realm}/clients); grant zte-gateway's service account
     the view-clients realm-management role.
  3. IdentitySyncService calls fetchClients() alongside the other three.
  4. PolicyMatcher/service2service/agentMcpToolCalls transition to the
     client:<clientId> URN prefix, validated against idp_identities like
     users2service already is; update the default zte-policies.yaml (and
     examples) to the new syntax.
  5. Admin Console — Identities DataGrid automatically supports CLIENT;
     Policy view highlights orphaned service2service/agentMcpToolCalls rules
     the same way it already does for users2service.

Deviations from literal task wording (see ADR-015 for full reasoning):

- IdentityUrn.parse gained a *category-aware default type*
  (parse(source, defaultType)) rather than a hardcoded ROLE default with
  client: treated as "just another prefix." Reusing the ROLE-default parser
  unchanged for service2service/agentMcpToolCalls orphan-checking would have
  made every single pre-existing bare-clientId rule (source: agent-a)
  immediately show up as orphaned the moment orphan-checking was extended to
  those categories, since client ids don't exist as ROLE-type cache entries.
  users2service kept calling the original one-argument parse(source), now a
  thin delegate to parse(source, IdentityType.ROLE) — verified behaviorally
  identical by a new test (oneArgOverload_isEquivalentToRoleDefault).
- fetchClients() fetches ALL clients in the realm (Keycloak built-ins like
  account/broker/admin-cli included), not just serviceAccountsEnabled ones —
  the task's own Self-Criticism explicitly green-lit this as acceptable MVP
  simplicity; Keycloak's Admin REST API has no server-side
  serviceAccountsEnabled filter on the /clients list endpoint anyway, so
  filtering would mean fetch-everything-then-filter-client-side for a purely
  cosmetic Identities-tab improvement — listed in ADR-015's Future Migration
  Path instead of implemented now.
- Schema: widened idp_identities' existing VARCHAR+CHECK constraint
  (V6__add_client_identity_type.sql: DROP CONSTRAINT idp_identities_type_check
  / ADD CONSTRAINT ... CHECK (type IN (...,'CLIENT'))) rather than a new
  column or a parallel client_identities table — keeps every identity kind
  (including machine identities) in one cache with one query/search/UI code
  path, which is the whole point of "unify the identity model," not a
  structural fork.
- Orphaned-rule checking's per-rule onErrorResume (added live in the
  previous ADR-014 session, after finding the Flyway/R2DBC startup race) is
  what makes merging three category streams (Flux.merge across
  users2service/service2service/agentMcpToolCalls) safe — without it, one
  category's query failure could have silently dropped another category's
  result the same way the original single-category version did before that
  fix. Confirmed this precondition held before extending the check to more
  streams, rather than assuming it would "just work."
- Updated the shipped zte-policies.yaml and docs/examples/zte-policies-example.yaml
  to the new client: syntax as asked, but explicitly verified (and stated in
  ADR-015) that this isn't a breaking change for any other deployment's
  existing bare-form rules — enrichClient's backward-compatible enrichment
  (returns both the bare clientId and the client:-prefixed form) means old
  rules keep matching unchanged; the shipped file was updated to demonstrate
  the clearer, now-validated form, not because the old form stopped working.

Verification performed: new/updated unit tests for IdentityUrn (client:
prefix, defaultType overload, one-arg-equivalent-to-ROIE-default),
IdentitySources (enrichClient), OrphanedRuleChecker (service2service CLIENT

real Testcontainers Keycloak Admin REST API — the actual proof the new
view-clients realm-management role grant works.
