# Context
User request (verbatim): "target2mcp rules should contain not only tool name
but also MCP identifier to avoid mismatches"

Raised as a direct architectural review comment after Stages 1-6 of the
ACAP/DIGI-KAI governance-demo plan were complete (ADR-019 through ADR-022),
plus the follow-up "should we update hubspotMCP list of tools to match the
scenario" exchange that surfaced two stale-process issues (gateway,
mcp_backend_bridge.py) — both restarted and verified working, including a
live Inventory Registry schema re-fetch confirming all 12 hubspot-mcp tools.

The concern: agentMcpToolCalls/agentMcpToolHolds rules match a tool call
purely by target (tool name) — no notion of which MCP backend that name
belongs to. Harmless today (only one configured backend, mcp-backend.uri),
but a real latent risk: a rule authored against one backend's tool
semantics could silently keep matching a same-named tool if the gateway is
ever repointed at a different backend.

## Clarifying question asked and answered
Two design forks were possible: (a) add an mcpTarget field to PolicyRule,
matched against the existing mcp-backend.name config value — scoped,
backward-compatible, no new routing infrastructure; (b) build real
multi-backend MCP routing first (registry-driven, mirroring
InventoryRouteDefinitionLocator's REST story), then extend rules to
disambiguate concurrently-routed backends. User chose (a) — the
recommended, smaller option, since there's still only one real backend
today and (b) would be building routing infrastructure nothing needs yet.

## Instructions
1. Add mcpTarget to PolicyRule, nullable, with a backward-compatible
   convenience constructor (every existing 7-arg call site across ~8 files
   must keep compiling unchanged).
2. Extend PolicyMatcher.evaluate/matchAny with new overloads accepting an
   mcpIdentifier parameter, rather than changing the existing signatures —
   the three REST authorization filters (ZteAuthorizationFilter,
   ServiceToServiceAuthorizationFilter, AdminAuthorizationFilter) must not
   need to change at all.
3. "Unscoped means universal" — a rule with no mcpTarget matches regardless
   of backend, mirroring pathPattern/methods' existing convention exactly
   (used by REST categories, unused by MCP — this is the inverse).
4. YamlMcpPolicyEngine injects mcp-backend.name (same config value
   LoggingMcpAuditService already uses for target_service) and passes it to
   every PolicyMatcher call.
5. Update this repo's own zte-policies.yaml for real, not just document the
   field: scope every per-agent ALLOW grant and both agentMcpToolHolds
   entries to mcpTarget: hubspot-mcp. Deliberately leave the three
   name-shape DENY safety nets (delete*, drop*, export_all_data) unscoped —
   that protection should hold regardless of which backend is configured.
6. Check PolicyValidator's duplicate-rule detection for a gap once
   mcpTarget can differentiate otherwise-identical rules — found one (the
   dedup tuple didn't include mcpTarget, so two legitimately-different
   rules scoped to different backends would have been flagged as a false
   duplicate/conflict) and fixed it, with regression tests for both the
   false-positive case and the still-correctly-flagged true duplicate.
7. Full test coverage: PolicyMatcher overload behavior (including the
   deliberate "5-arg overload + mcpTarget-scoped rule = no match" edge
   case, consistent with pathPattern/methods precedent), YamlMcpPolicyEngine
   end-to-end scoped/unscoped/mismatched-backend scenarios, PolicyValidator
   regression tests.
8. Surface mcpTarget in the Admin Console's Policies tab (new column).
9. ADR (next number), CLAUDE.md/SPECS.md/README.md/policy-schema.md
   doc-sync — including fixing two more now-noticed stale "three
   categories"/missing-ADR-index-row references left over from earlier
   stages, this prompts-hist file.
