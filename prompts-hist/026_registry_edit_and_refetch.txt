Registry inline edit + confirmed refetch-overwrite — prompt from "Senior
Solution Architect / React Developer" role, a frontend-focused follow-up
to the docs_url/sync-fetch amendment (025_custom_docs_url_and_sync_fetch.txt).

Original prompt (paraphrased — full text requested CoT/Self-Criticism per
CLAUDE.md): the backend already supports PUT-based updates and
synchronous schema fetch; the Admin UI has no explicit "Edit" action, and
the existing "Fetch" (🔄) button needs confirming as a true "Refetch" that
overwrites any previously captured schema, not just a first-fetch-only
action.

Instructions given: verify PUT /api/v1/admin/inventory/{id} and
InventoryService.update handle docsUrl/managementUrl correctly (no
backend changes if already implemented); add an Edit (✏️) icon button to
the Registry table; wire it to the existing onboarding Dialog in an
"Edit Mode" pre-filled with the row's data, submitting via PUT instead of
POST; dialog title changes contextually; ensure form state fully resets
on modal close (the task's own Self-Criticism: don't let a previous
edit's values leak into the next "New" onboarding); confirm the
synchronous fetch endpoint allows overwriting an existing
discovered_schema without conflict.

---

Backend verification came first, as instructed, and genuinely required no
changes — confirmed by reading the actual code, not assumed from the
task's own "(No changes needed if already implemented)" hint:
InventoryService.update already threads docsUrl/managementUrl through to
InventoryRepository.updateFields (both added in the 025 amendment), and
that native @Query already sets both columns unconditionally. The
synchronous fetch path (AutoDiscoveryWorker.fetchSchemaNow ->
InventoryService's persist -> InventoryRepository.updateDiscoveredSchema)
is a plain UPDATE ... SET discovered_schema = CAST(:schema AS jsonb)
WHERE id = :id with no prior-value check or uniqueness constraint on that
column at all — there is no code path that could produce a "conflict"
here, so "ensure it allows overwriting without throwing a conflict" was
already unconditionally true. No backend files touched this session.

Frontend: added a single editingService (InventoryEntry | null) state to
Inventory.tsx, reusing the same onboarding Dialog and its existing
formX fields (chose local component state over a separate editRecord
prop, since the Dialog was never extracted to its own component — matches
the task's own "accept an optional editRecord prop or state" wording,
which explicitly allowed either). openEditDialog(service) pre-fills all
five form fields (including docsUrl/managementUrl, both using the
existing ?? '' null-to-empty-string pattern the onboarding form already
used) and sets editingService; the "Onboard Service" button now routes
through a symmetrical openCreateDialog() that clears both the form and
editingService first, so opening a fresh onboard dialog after closing an
edit dialog can never see stale values even without relying on close-time
cleanup alone.

Closed the actual gap the task's Self-Criticism specifically named: the
existing dialog previously reset form state only on a *successful*
submission (there was no equivalent for Cancel or backdrop-dismiss).
That was a latent, harmless quirk with only one dialog mode (leftover
typed values in an abandoned onboarding attempt), but becomes a real bug
the moment a second mode (Edit) exists — Cancel-ing out of editing one
service and then clicking "Onboard Service" would previously have shown
that service's stale values in what's supposed to be a blank form.
Fixed with one shared closeDialog() function wired to Dialog's onClose
*and* the Cancel button (previously two different, inconsistent
handlers) — both now always reset form state and editingService together.

handleOnboard was renamed handleSubmit and branches on editingService:
PUT `/api/v1/admin/inventory/{id}` when editing, the original POST
otherwise — same request body shape either way. Snackbar/dialog-title/
button-label copy all branch on editingService too ("Edit Service"/"Save"
vs. "Onboard Service"/"Onboard"), including an explicit "discovery
re-running in the background" success message for edits, since
InventoryService.update (pre-existing, unchanged) always resets status to
PENDING and re-triggers discovery — worth surfacing to the operator, not
silently different from what onboarding already tells them.

Verified live against the real gateway/Postgres: PUT-edited a real
registered service's managementUrl, confirmed the change persisted and
discovery re-ran; called the schema/fetch endpoint twice in a row against
an entry that already had hasSchema: true, confirming the second call
still returns 200 and genuinely re-executes the probe (not a no-op) —
matching this task's explicit "Refetch" framing.

Named, not fixed (out of this task's literal scope): InventoryService.update
still has no duplicate-name check the way create() does (existsByName is
only called from create) — renaming a service via PUT to collide with
another existing entry's name would currently surface as a raw
constraint-violation error rather than a clean 409, same class of gap as
several other pre-existing items already tracked in docs/SPECS.md §9.2.
Not touched here since the task's own backend instruction was narrowly
"double-check field application," not "add missing validation," and nothing about it changed with today's frontend
work.

ADR handling: amended ADR-016 again, in place — fifth amendment to this
stage's ADR, continuing the established pattern; this one is intentionally
short, since the actual change is a self-contained frontend feature with no
new backend surface.
