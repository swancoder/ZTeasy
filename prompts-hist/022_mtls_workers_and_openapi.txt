  1. Security vulnerability: AutoDiscoveryWorker and HealthPollingService
     use a plain WebClient, bypassing the mTLS perimeter — must use the

  2. Missing functionality: service-a/service-b lack OpenAPI docs, causing

---

**The single biggest deviation this session: Task 1's premise was
investigated and found to be factually incorrect, before writing any
code** (see ADR-016's new "Amendment" section for the full writeup and
verification evidence). `AutoDiscoveryWorker`/`HealthPollingService`
already inject the application's single Spring-Boot-autoconfigured default
`WebClient.Builder` — the exact same one `KeycloakIdpAdapter`/
`McpBackendClient` use — and that builder already carries the gateway's
mTLS client certificate whenever `zte.mtls.enabled=true` (the prod/dev
default), because `MtlsHttpClientConfig`'s single `ReactorClientHttpConnector`
bean gets automatically applied to every autoconfigured `WebClient.Builder`
via Spring Boot's own `ClientHttpConnectorAutoConfiguration` customizer
mechanism. Verified two independent ways, not assumed:
  - Bytecode inspection (`javap` on the actual `spring-boot-autoconfigure-3.4.3.jar`
    classes) confirmed `ClientHttpConnectorAutoConfiguration.webClientHttpConnectorCustomizer(...)`
    returns a `WebClientCustomizer` whose body is
    `builder -> builder.clientConnector(connector)`.
  - Live, against the real running gateway: `curl` with no client
    certificate against `service-a`'s `client-auth: need` mTLS listener
    (port 8081) fails at the TLS handshake with no HTTP response at all
    (server sends `Request CERT`, connection then dies). `AutoDiscoveryWorker`'s
    own probe against the identical URL, from the real app, received a
    genuine HTTP 404 — only possible if a valid client cert had already
    been presented during that handshake.
  There was also nothing to "remove" per Task 1's "remove any plain
  WebClient.create() instantiations" instruction — neither class ever used
  the static `WebClient.create()` factory; both always injected the
  standard `WebClient.Builder` bean.

Given this, the code change actually made for Task 1 was **Javadoc only**
— both classes now explicitly document the mTLS-inheritance fact, the
mechanism, and how it was verified, so a future reader (or task author)
doesn't have to re-derive it. Deliberately did NOT add a second, explicit
`ReactorClientHttpConnector` injection duplicating already-correct
behavior — that would have been pure redundancy, and a real regression
risk: the connector bean only exists when `zte.mtls.enabled=true`, and the
`it` integration-test profile deliberately sets it `false` (no certs
needed in CI) — a naive hard constructor dependency on that bean would
have broken every integration test's `ApplicationContext` startup for a
"fix" that duplicated behavior already present.

Task 2 (OpenAPI) was genuine, real work — implemented as asked:
`springdoc-openapi-starter-webflux-ui:2.7.0` added to both modules. No
`SecurityConfig` change was needed (a real, useful discovery, not assumed):
both `service-a` and `service-b` already run their own `ServiceSecurityConfig`
(`anyExchange().permitAll()` — mTLS is already their entire trust
perimeter; the shared `auth-library.SecurityConfig`'s JWT requirement
doesn't apply to either service), so springdoc's auto-registered
`/v3/api-docs` route is reachable the moment the dependency is added, with
zero extra authorization wiring.

Task 3 (`InventoryRegistryIT` update) was deliberately **not** done as
literally described, for a concrete, verified reason: the task's
instruction assumed this IT tests directly against real `service-a`/
`service-b` processes — it doesn't. Per `BaseZteIntegrationTest`,
`service-a.uri`/`service-b.uri` point at an in-process WireMock stand-in,
by design, so the IT suite needs no real service-a/b process or cert setup
to run. The existing `onboardRestService_discoverySucceeds_becomesActive`
(stubs `/v3/api-docs` → 200 → ACTIVE) and `onboardRestService_discoveryFails_becomesWarning`
(no stub → 404 → WARNING) tests already correctly cover both outcomes and
remain valid regardless of whether this repo's own two example services
now happen to have OpenAPI docs — a registered service that genuinely
lacks docs must still land on WARNING. This feature's actual claim ("service-a
now really exposes /v3/api-docs") was verified live instead — running
service-a with the new dependency, curling `/v3/api-docs` through mTLS,
then registering it in the real running gateway's inventory and confirming
ACTIVE, not WARNING — matching the task's own literal Verification section,
which itself asks for a live `bootRun`+`curl` check, not a new automated test.

ADR handling: amended the existing ADR-016 in place (a new "Amendment"
section, same pattern ADR-013's same-day audit-exclusion amendment
established) rather than creating a new ADR file — there was no new
architectural decision here (the mTLS wiring was already correct; adding
springdoc is a dependency addition, not a structural decision), just a
correction and a small, well-scoped addition to an existing one.
