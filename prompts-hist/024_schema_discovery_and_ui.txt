API Catalog: capture discovery payloads and render them in the Admin UI —
prompt from "Senior Solution Architect / Full-Stack Java & React Developer"
role, filed as a feature evolution of the existing AutoDiscoveryWorker
(ADR-016, Stage 16), which until now only checked reachability of
/v3/api-docs and tools/list and discarded the response body.

Original prompt (paraphrased — full text requested CoT/Self-Criticism/ADR
protocol per CLAUDE.md):
  Store the raw response body from a successful discovery probe (OpenAPI
  document for REST, JSON-RPC tools/list response for MCP) in a new JSONB
  column on inventory_services, expose it via a dedicated on-demand REST
  endpoint (not embedded in the list view, to avoid degrading it), and
  render it in the Admin Console: swagger-ui-react for REST targets, a
  plain MUI list of tool name/description for MCP targets.

Instructions given: Flyway migration for a discovered_schema JSONB column;
update AutoDiscoveryWorker to extract and persist the body on success;
GET /api/v1/admin/inventory/{id}/schema for on-demand fetch; add
swagger-ui-react to zt-admin-ui, a "View Schema" action opening an MUI
Drawer, REST renders via <SwaggerUI spec={...}/>, MCP renders tools via
MUI List/ListItem/Typography; Self-Criticism named the R2DBC JSONB mapping
risk and empty/invalid JSON handling explicitly; ADR Protocol: amend
ADR-016 again (same pattern as the two prior same-day/next-day amendments
this stage already has).

---

Investigated before implementing, not assumed: whether Spring Data R2DBC
can map a Postgres jsonb column to a plain Java String without a custom
converter — this project has zero prior JSONB usage to copy from.
Decompiled r2dbc-postgresql 1.0.7.RELEASE's codec classes (javap) and
found a dedicated JsonStringCodec registered in DefaultCodecs specifically
for decoding json/jsonb columns into java.lang.String — confirms reads
work with a plain String target with no custom converter needed. Writes
are the asymmetric half: the driver's default bind for a String parameter
is VARCHAR, and Postgres rejects an implicit varchar->jsonb assignment in
a parameterized UPDATE, so InventoryRepository.updateDiscoveredSchema uses
an explicit CAST(:schema AS jsonb) in the native @Query — exactly the
mitigation the task's own Self-Criticism suggested, now with the concrete
reasoning for why it's necessary (not just copied blindly).

Bigger design choice, not spelled out as literally in the task: kept
discovered_schema completely OFF InventoryEntry/InventoryView and
findAll(). InventoryRepository gets two new methods (updateDiscoveredSchema,
findDiscoveredSchemaById) that operate as native, single-purpose queries
independent of the entity mapping ReactiveCrudRepository/InventoryService.list()
use. This satisfies the task's own explicit goal ("prevent performance
degradation of the main list view") by construction — the list/CRUD path
literally never selects this column, rather than relying on callers to
remember not to over-fetch it. Zero changes needed anywhere else in the
already-existing InventoryEntry/InventoryView/AdminInventoryController.InventoryRequest/
frontend types.ts as a direct result — this ADR-016 amendment's blast
radius on existing, working code is limited to AutoDiscoveryWorker
(genuine logic change) and one new controller endpoint + repository
method pair.

AutoDiscoveryWorker: switched probeRestApiDocs/probeMcpToolsList from
.toBodilessEntity() to .retrieve().bodyToMono(String.class) to actually
capture the body. Found and fixed a real regression this switch would
otherwise have introduced, not caught by review alone but by re-reading
what toBodilessEntity() actually guarantees: it always emits exactly one
element regardless of body length, but bodyToMono(String.class) on a
genuinely empty (0-byte) response body completes empty — no element at
all — which would have silently broken the existing "2xx with an empty
body is still ACTIVE" case (the CRUD test's onboard() stub does exactly
this: aResponse().withStatus(200) with no body). Fixed with
.defaultIfEmpty("") right after bodyToMono, restoring the original
always-emits-one-element guarantee while still capturing whatever text
existed.

Added a JSON-validity guard (Jackson ObjectMapper#readTree) before ever
calling updateDiscoveredSchema — a genuinely necessary correctness
measure, not speculative: a target returning 200 with a non-JSON body
(an HTML error page at /v3/api-docs, for instance) would otherwise make
Postgres reject the CAST(text AS jsonb), and because that write is
chained after the status-update write via .then(...), a naive
implementation would let a malformed body's cast failure also blow up the
ACTIVE status write it's chained to — status still gets committed first
via the .then() ordering either way, but the failure would surface as an
unhandled error in InventoryService.triggerDiscoveryAsync's subscribe
error callback instead of being handled gracefully. Blank bodies (the
empty-200 case above) are treated identically to invalid JSON — skip the
schema write, keep the status write — since an empty string isn't valid
JSON either and Postgres would reject casting it the same way.

Testing: AutoDiscoveryWorker has never had a mocked-WebClient unit test
(established precedent — proven only via InventoryRegistryIT against real
WireMock targets, same as KeycloakIdpAdapter/McpBackendClient). Kept that
precedent rather than introducing a new pattern; added four new IT cases
instead (REST capture round-trip, MCP capture round-trip, 404-on-nothing-
captured for both a WARNING service and an unknown id). The REST/MCP
capture tests initially failed on their first real run — not because the
capture pipeline was broken, but because the test asserted the exact
original response-body string, and Postgres's jsonb column type
canonicalizes on write (reorders keys, normalizes whitespace) rather than
preserving the original text byte-for-byte. Found live running the suite,
not anticipated in advance; fixed by comparing parsed Jackson JsonNode
trees (structural equality) instead of raw strings — the fix also stands
as a second, independent confirmation that the write(CAST)->read
(JsonStringCodec) round trip actually produces semantically correct JSON,
not just "no exception was thrown."

Frontend: swagger-ui-react@5.32.13 + @types/swagger-ui-react@5.18.0 added
as instructed. npm install surfaced a real, worth-recording detail: one of
swagger-ui-react's transitive deps (react-inspector@6.0.2) declares a
peer range of React 16-18, not 19 — npm resolved it anyway (a warning, not
a hard failure) and both `tsc -b` and `vite build` succeeded cleanly, so
left as-is rather than forcing an override the project doesn't need yet;
worth revisiting if swagger-ui-react itself ever hard-fails at runtime on
React 19 (not observed). Also worth recording plainly: adding this
dependency roughly tripled the built bundle size (589KB -> 1.88MB raw,
177KB -> 538KB gzipped) — a real, direct cost of the library choice the
task specified, not something this amendment tried to work around (e.g.
via dynamic import/code-splitting), since the task didn't ask for that and
the codebase's established bias is against unrequested infrastructure.

New SchemaDrawer.tsx component (not inlined into Inventory.tsx, to keep
that file from growing past its existing CRUD-table-plus-onboarding-dialog
scope) — fetches the schema only when a row's new "View Schema" icon
button is clicked (on-demand, matching the backend), parses it with
JSON.parse guarded by a try/catch (falls back to showing the raw text in
a <pre> block with an error Alert if parsing fails — the task's own
Self-Criticism instruction), and branches on targetType: <SwaggerUI
spec={parsed}/> for REST, a small defensive tree-walk extracting
result.tools[] (typeof/Array.isArray guards throughout, since this is an
external service's response shape, not something this codebase controls)
into an MUI List for MCP.

ADR handling: amended ADR-016 again, in place — third amendment to this
stage's ADR, following the same pattern the two prior mTLS/OpenAPI and
management-URL amendments already established for this file.
