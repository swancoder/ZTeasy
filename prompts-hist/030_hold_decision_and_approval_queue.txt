# This stage's scope (Stage 1 of 6)
Add HOLD as a first-class MCP policy decision outcome, plus a durable
approval queue so a human can approve or reject a held call.

## Instructions
1. Verify the exact current shape of PolicyDecision/McpPolicyEngine/
   YamlMcpPolicyEngine/PolicyRule/PolicyMatcher/McpProxyHandler before
   designing anything (an Explore agent had already done this in the prior
   planning phase — reuse those findings, re-read the specific files before
   editing).
2. Design HOLD so it does NOT require adding a third RuleEffect value shared
   by users2service/service2service (those categories' authorization filters
   switch exhaustively over PolicyEvaluation.Outcome and have no meaningful
   notion of "hold" — check for this exhaustive-switch constraint directly in
   the code, don't assume). Prefer a separate, MCP-only agentMcpToolHolds
   rule list matched independently.
3. pending_approvals must be DB-backed (R2DBC + Flyway), not in-memory — a
   held item may be reviewed well after the originating SSE session closes.
4. Add POST /api/v1/admin/approvals/{id}/approve|reject (AdminApprovalsController)
   and a GET list endpoint, gated by the same u2s-admin-console-api rule as
   every other admin controller.
5. New Admin Console "Approvals" tab (Approve/Reject buttons, reject behind
   a confirm dialog).
6. Register a new Keycloak client crm-account-health-emea-01 and give it
   read grants + hold-on-send_email/draft_followup in zte-policies.yaml, so
   this stage is independently testable end-to-end before Stage 5
   (hubspot-mcp tool alignment) exists.
7. Update every existing test/call site broken by the change; add new unit
   tests for the new matching/service logic; add an IT scenario exercising
   hold → admin approve → backend call.
8. ADR (next number), CLAUDE.md Stage Index, docs/SPECS.md (targeted
   sections), README.md (targeted sections), docs/policy-schema.md, this
   prompts-hist file.
9. Compile and run ./gradlew test (and integrationTest if Docker is
   available) before considering the stage done.

## Self-Criticism (carried into the ADR)
- A held item's decision can't be pushed back into the agent's SSE session
  if that session has since closed — the decision still executes and is
  audited, but the agent itself never learns the outcome under MCP's current
  session model. Accepted for this stage; flagged as a real gap, not solved.
- route_to (from ACAP's hold[].route_to) is stored but not wired to any real
  per-reviewer routing/notification.
- decidedBy trusts the calling admin's JWT claims at face value; no check
  that the specific human matches ACAP's named approver (that concept
  doesn't exist yet).
