## Instructions
1. No new table — request_logs (ADR-013/ADR-017) already carries everything
   needed (agent_id, tool_name, decision_effect, timestamp, message). This
   stage is new read queries + UI only.
2. Per-agent ALLOW/HOLD/DENY activity summary over a selectable time window,
   and a live "out-of-policy attempts" feed (recent denials).
3. Aggregate/group in Java, not a SQL GROUP BY + projection — matches
   InventoryService's own established "join/aggregate in Java at this
   demo's scale" precedent rather than introducing a new, more fragile
   R2DBC projection pattern.
4. Scope the out-of-policy feed to MCP-agent traffic specifically (agent_id
   IS NOT NULL), distinct from the existing Audit Trail tab's REST+MCP-wide
   view — this is an AGENT governance view. Confirm decisionEffect=DENY
   alone already covers a human's post-hold REJECTED decision too (it does,
   per ADR-019's mapping) without new logic.
5. Optional per the plan: a simple compliance export. Implemented as a
   plain JSON snapshot of the two views above (no new formatting/aggregation
   period) via a GET endpoint + a client-side download button — not a
   separately-formatted compliance document, which would be speculative
   generality for a single demo.
6. New Admin Console "Governance" tab wired into App.tsx's existing
   View-union + Tab + conditional-render pattern.
7. Unit test the aggregation logic thoroughly (GovernanceService); rely on
   existing precedent (thin admin controllers have no dedicated test in
   this codebase) for the controller layer.
8. ADR (next number), CLAUDE.md/SPECS.md/README.md doc-sync, this
   prompts-hist file.
