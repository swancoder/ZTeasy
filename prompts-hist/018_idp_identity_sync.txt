Original prompt (paraphrased — full text requested CoT/Self-Criticism/ADR
protocol per CLAUDE.md, and gave six numbered task groups plus verification

  Transition users2service policies from direct realm-role mapping to an
  IdP-backed identity model (Users, Groups, Roles). Build an adapter-based
  synchronization engine that caches IdP metadata in PostgreSQL, and update
  the policy matcher to support URN-prefixed sources.

Task groups as given:
  1. Keycloak config — zte-gateway (or a new dedicated client) needs Service
     Accounts Enabled + view-users/view-realm roles from the realm-management
     client.
  2. Flyway migration — idp_identities table: id (UUID), type
     (USER/GROUP/ROLE), external_id (unique with type), name, display_name,
     last_synced.
  3. IdpClient interface (fetchUsers/fetchGroups/fetchRoles) +
     KeycloakIdpAdapter using WebClient with client-credentials token;
     zte.idp.provider=keycloak conditional injection for a future non-Keycloak
     adapter.
  4. IdentitySyncService, @Scheduled every 15 min, UPSERT via R2DBC;
     POST /api/v1/admin/identities/sync manual trigger; GET
     /api/v1/admin/identities/search?type=&q= for UI autocomplete.
  5. PolicyMatcher URN support (user:<name>/group:<name>/role:<name> in
     source); validate zte-policies.yaml sources against idp_identities on
     load/reload, log a severe warning for orphaned rules but never
     reject/delete.
  6. New "Identities" tab in zt-admin-ui (DataGrid: Type, Name, Display Name,
     Last Synced) with a "Sync Now" button; Policy view highlights rules
     whose source isn't in the local cache.

Deviations from literal task wording (see ADR-014 for full reasoning):

- PolicyMatcher itself needed zero code changes — it already does generic
  AntPathMatcher string-list matching over whatever `sources` list is
  passed in. The URN feature lives entirely in the callers
  (ZteAuthorizationFilter/AdminAuthorizationFilter): a new
  IdentitySources.enrich(roles, jwtAuth) helper builds an enriched list —
  bare role names (unchanged, so every existing rule keeps matching) plus
  role:<r>/user:<name>/group:<g> URNs — passed to policyMatcher.evaluate()
  instead of the bare roles list. The bare roles list is kept for the
  service2service dispatch check and audit logging at both call sites.
- Orphan-checking was deliberately kept out of PolicyValidator/PolicyMatcher
  (ADR-009 §8.2 requires PolicyMatcher.evaluate() stay synchronous/zero-I/O
  for MCP's inline call). Instead: PolicyDefinitionStore.doReload() now
  publishes a new PolicyDocumentReloadedEvent (Spring
  ApplicationEventPublisher/@EventListener — new pattern in this codebase)
  only on successful reload, and a new OrphanedRuleChecker listens for it
  plus runs its own @PostConstruct startup check. Named, accepted race
  condition: this startup check can run before IdentitySyncService's own
  first @Scheduled sync populates idp_identities, producing a transient
  false-positive warning that self-corrects within one sync interval or
  after a manual sync/reload.
- UPSERT is a real Postgres INSERT ... ON CONFLICT (type, external_id) DO
  UPDATE via @Modifying @Query, not repository.save() — save()'s "null id =
  new" convention would violate the unique constraint on the second sync
  cycle for the same identity.
- Reused zte-gateway's existing service account (already
  serviceAccountsEnabled, known secret) rather than a new dedicated Keycloak
  client — the task explicitly offered both options; reusing avoids a
  second secret to manage.
- Added an oidc-group-membership-mapper to zte-gateway (claim `groups`,
  full.path: false) as a real prerequisite for group: rules to ever match
  anything — Keycloak only emits claims an explicit mapper requests, same
  as the existing realm_access.roles/preferred_username mappers already
  needed. zte-realm has no groups defined yet, so this is implemented but
  currently unexercised — named explicitly in ADR-014, not silently gapped
  or faked with an invented demo group.
- UI cross-references orphan status client-side: PolicyDashboard.tsx
  independently fetches /api/v1/admin/identities/search and does its own
  small (~10-line), intentionally duplicated TypeScript port of
  IdentityUrn.parse's logic, rather than adding a backend field to the
  shared PolicyRule/PolicyDocument shape (used by service2service/MCP too,
  where "orphaned" is meaningless) or a dedicated orphaned-rule-ids
  endpoint.
- "DataGrid" (task's literal word, Task 6) implemented as a plain MUI Table
  (Identities.tsx, mirroring AuditTrail.tsx) rather than @mui/x-data-grid —
  same "no new dependency with unproven compatibility on this MUI v9/React
  19 combo" call already made in ADR-013 for the Audit Trail tab.

Live-testing finding (see ADR-014's dedicated "Finding" section):
restarting the gateway against a real, already-provisioned Postgres (Flyway
at version 4) surfaced that OrphanedRuleChecker's @PostConstruct queried
idp_identities via R2DBC before Flyway's V5 migration (JDBC-based) had run
— no automatic ordering guarantee exists between Flyway and R2DBC-backed
beans, and this was the first eager (@PostConstruct-time) R2DBC caller in
the codebase, so the gap had never been exercised before. Compounding
effect: two concurrent per-rule queries both failed, and flatMap's
single-error propagation silently dropped the second failure as
onErrorDropped. Fixed with a per-rule onErrorResume so one query failure
degrades to a log line instead of taking down the whole check or producing
a confusing dropped-error stack trace — added a corresponding unit test
(oneRuleQueryFailure_doesNotStopCheckingOtherRules). Not caught by any
mocked unit test; found only by recreating the Keycloak container, running
the real gateway against the real dev stack, and reading the startup log.
